# 0. Executive Proposition

Unfict SHALL use a proprietary iconography and motif system derived from the visual grammar of the canonical Unfict mark.

The purpose is not decoration.

The purpose is to create:

- instant visual recognition;
- low-distraction interface personality;
- semantic consistency;
- continuity between website and product;
- a distinctive diagram language;
- a scalable visual vocabulary that remains recognizably Unfict without forcing the logo into every surface.

The governing proposition is:

> **Minimum visual distraction. Maximum recognizable character.**

The system SHALL be distinctive enough to feel owned by Unfict and familiar enough that common interface actions remain immediately understandable.

The system is therefore deliberately divided into:

```text
A. BRAND MOTIFS
   expressive / ownable / abstract

B. FUNCTIONAL UI ICONS
   familiar / usable / Unfict-characterized

C. DOMAIN & CONCEPT ICONS
   semantic / Unfict-specific / explanatory
```

The three layers SHALL NOT be conflated.

---

# 1. Why This System Exists

Unfict’s Brand requires an Institutional Infrastructure character.

That creates a design tension.

If Unfict uses only:

- typography;
- whitespace;
- thin borders;
- neutral fields;

the experience can become sterile.

If Unfict solves that problem with:

- generic illustrations;
- excessive gradients;
- decorative cards;
- stock icon packs;
- random abstract shapes;

the experience loses authority and visual ownership.

The iconography system resolves that tension by providing a **small, repeatable, proprietary visual language** that can create personality without increasing visual noise.

---

# 2. Core Design Principle

# **Recognizable Before Decorative**

Every icon must first succeed at its semantic Job.

Brand distinctiveness comes second.

For universal actions such as:

- search;
- close;
- edit;
- copy;
- download;
- settings;

the icon SHALL remain conventionally recognizable.

Unfict’s visual grammar may alter:

- terminal shapes;
- corner character;
- diagonal tension;
- internal cut;
- fill accent;
- proportion;
- optical weight;

but SHALL NOT make the action harder to understand.

The governing rule:

> **Never sacrifice usability to prove that an icon is custom.**

# 4. Canonical Asset Immutability

The AI Agent SHALL NOT:

- redraw the Unfict mark from visual memory;
- trace the PNG;
- approximate the mark using rounded polygons;
- rebuild the wordmark with a font;
- recolor the canonical source;
- stretch the canonical mark;
- normalize its proportions;
- “improve” its curves;
- merge its two canonical pieces;
- rotate the canonical mark;
- change the internal spacing of the canonical mark.

If a derived icon uses mark-inspired geometry:

> **derive visual grammar from the canonical vector; do not modify the canonical mark itself.**

# 5. Visual DNA of the Unfict Mark

The system derives from these observed characteristics:

## 5.1 Separation

The canonical mark uses **two separated forms**.

This creates:

- relation without fusion;
- movement without a literal arrow;
- continuity across space;
- distinct states connected conceptually.

This separation is a core source of Unfict personality.

---

## 5.2 Directionality

The forms imply movement along a rising diagonal.

For derived motifs, use a primary directional family around:

> **approximately 36° ± 4°**

only where directionality is semantically useful.

This is a visual grammar target, not permission to rotate every icon.

---

## 5.3 Soft Aerodynamic Geometry

The forms combine:

- substantial mass;
- rounded ends;
- controlled asymmetry;
- slanted directional edges;
- clean negative space.

They should feel:

- purposeful;
- calm;
- kinetic;
- modern;

not:

- bubbly;
- playful;
- cartoonish.

---

## 5.4 Controlled Negative Space

The gap between forms matters.

Derived icons may use negative space to indicate:

- transfer;
- distinction;
- request/resource separation;
- source/destination;
- bounded scope;
- before/after;
- relationship.

Negative space SHALL NOT become arbitrary decoration.

---

## 5.5 Blue as Identity Signal

Canonical Unfict Blue:

`#1965EC`

Blue identifies Unfict.

It should not automatically fill every icon.

The icon system SHALL preserve Brand discipline:

> **Blue signals Unfict, active meaning, or brand ownership. It does not become visual wallpaper.**

# 6. Three-Layer System

---

# 6.1 Layer A — Brand Motifs

Purpose:

- brand recognition;
- section accents;
- environmental graphics;
- transitions;
- diagram anchors;
- empty-state signatures;
- subtle motion.

Brand motifs MAY be abstract.

They do not need universal semantic recognition because they are not standalone action controls.

---

# 6.2 Layer B — Functional UI Icons

Purpose:

- ordinary interface actions;
- navigation;
- controls;
- system interaction.

These icons MUST remain familiar.

Examples:

- search;
- close;
- menu;
- copy;
- settings;
- delete.

Unfict character SHALL be subtle.

---

# 6.3 Layer C — Domain & Concept Icons

Purpose:

- concepts specific to Unfict;
- domain semantics;
- explanatory diagrams;
- capability families;
- product navigation where authorized;
- educational content.

These may be more distinctive than functional icons because universal conventions often do not exist.

They must still have governed semantics.

---

# 7. Cross-Cutting Rule — Icon Existence ≠ Capability Availability

Creating an icon for:

- Authority;
- Evidence;
- Policy;
- Delegation;
- Host;
- Receipt;
- Trust-related concepts;

DOES NOT authorize:

- public marketing of the concept;
- product navigation exposure;
- user access;
- roadmap representation;
- capability activation.

The icon library is a design vocabulary.

Capability visibility remains governed by product, ZyUX, authorization, and market-scope authorities.

---

# 8. Master Grid

The primary production grid SHALL be:

# **24 × 24**

All standard UI icons are authored first on a 24 × 24 master frame.

---

# 8.1 Safe Zone

Preferred visible geometry:

```text
20 × 20
```

centered within the 24 × 24 frame.

Ordinary inset:

```text
2 units each side
```

Optical overshoot MAY reach approximately 0.5 unit beyond the preferred safe zone where necessary for circles, diagonals, or perceived alignment.

---

# 8.2 Secondary Sizes

The system SHALL support:

```text
16 px — compact / dense controls
20 px — compact default
24 px — standard default
32 px — prominent controls / small concept icons
40 px — domain / feature marker
48 px — feature / empty-state
64 px+ — editorial / explanatory
```

Do NOT assume mechanical scaling is sufficient below 20 px.

---

# 9. Small-Size Optimization

Icons at 16 px and 20 px may require simplified variants.

The AI Agent SHALL test:

- interior gaps;
- line intersections;
- negative spaces;
- small blue accents;
- diagonal clarity.

At 16 px:

- remove nonessential detail;
- widen critical gaps;
- avoid micro-cutouts;
- preserve the recognized silhouette.

A 64 px domain icon shrunk to 16 px without optical correction is NOT acceptable.

---

# 10. Functional Icon Stroke System

Functional UI icons SHOULD default to a monoline construction.

Master 24 px target:

```text
Stroke width: 2 px
Line cap: round
Line join: round
```

For 20 px:

```text
Stroke target: approximately 1.75–2 px
```

For 16 px:

```text
Stroke target: approximately 1.5–1.75 px
```

Final values are subject to optical consistency across the set.

---

# 11. Filled Geometry

Use filled geometry when:

- the icon is a Brand Motif;
- a domain icon requires a Unfict-owned anchor;
- a selected/active state legitimately benefits from fill;
- a small structural accent is clearer as fill.

Avoid making every functional icon a solid filled object.

---

# 12. Unfict Signature Treatments

An icon may express Unfict character through ONE OR MORE of the following, but never all merely for decoration:

## A. Signature Diagonal

One structural edge or movement axis may follow the approximately 36° visual family.

## B. Rounded Directional Terminal

A terminal may use a softened, weighted end inspired by the mark.

## C. Controlled Cut / Gap

A negative-space break may distinguish:

- source from destination;
- current from next;
- entity from resource.

## D. Blue Anchor

A small filled blue element may identify the Unfict-owned part of a semantic composition.

## E. Two-Part Relationship

Two separate forms may express a relationship without becoming literal arrows.

The Agent SHALL choose the least intrusive signature treatment that preserves recognition.

---

# 13. Signature Restraint Rule

For universal controls:

> **Use at most one obvious Unfict signature treatment.**

For domain icons:

> **Use at most two signature treatments unless the icon is explicitly a Brand Motif.**

This prevents icons from looking overdesigned.

Do not hard-code:

- red;
- green;
- orange;

inside the core icon asset merely because the icon represents error/success/warning.

The geometry should work using `currentColor`.

Semantic state color SHALL come from the governing UI token system.

This preserves:

- theme flexibility;
- accessibility;
- consistency.

---

# 15. Monochrome Requirement

Every functional and domain icon SHALL work in monochrome.

A blue accent may enhance the icon.

It SHALL NOT be required to understand it.

This prevents:

- color-only semantics;
- dark-mode failures;
- print failures;
- accessibility failures.

---

# 16. Dark Surface Rule

When used on authorized dark surfaces:

- use white / appropriate foreground token;
- Unfict Blue may remain where contrast is sufficient;
- do not invent a new dark-surface brand palette here.

Dark use must remain exceptional under BRAND-001.

---

# 17. Icon Naming Standard

Canonical file IDs SHALL use lowercase kebab-case:

```text
uf-icon-search
uf-icon-copy
uf-icon-resolver
uf-icon-identity
uf-icon-receipt
```

SVG filenames:

```text
uf-icon-search.svg
uf-icon-resolver.svg
```

Component names MAY use PascalCase:

```text
UfIconSearch
UfIconResolver
```

Do not use ambiguous names such as:

```text
icon-thing
icon-arrow2
blue-symbol
shape-final
```

---

# 18. Variant Naming

Allowed suffixes only when semantically required:

```text
-16
-20
-24
-active
-filled
-outline
```

Do not generate:

```text
-final
-final2
-new
-v3-real
```

Versioning belongs in source control / design history.

---

# 19. Machine-Readable Icon Specification

Every governed icon SHALL have a semantic record.

Recommended schema:

```yaml
id: uf-icon-resolver
family: domain
semantic_name: Resolver
meaning: Infrastructure that resolves identity/request context to an appropriate resource relationship.
does_not_mean:
  - authenticity proof
  - authorization
  - physical movement
  - content management
primary_uses:
  - resolver education
  - technical diagrams
  - authorized resolver navigation
avoid_uses:
  - generic routing icon
  - security verification
familiarity_requirement: domain-specific
construction:
  base_grid: 24
  mode: hybrid
  unfict_signature: controlled-junction-with-blue-anchor
small_size_variant: true
color_default: currentColor
blue_accent_allowed: true
accessibility_label_behavior: contextual
status: governed
```

The AI Agent SHALL generate or maintain this metadata for every icon.

# 72. AI Agent Evaluation — Universal Functional Icons

For each functional icon, ask:

### Recognition Test

Could a competent user identify the action without seeing the Unfict logo?

If NO:

> simplify.

### Brand Test

Does the icon have a subtle Unfict character when compared side-by-side with a generic icon?

If NO:

> add the minimum viable signature.

### Overdesign Test

Does the brand signature interfere with recognition?

If YES:

> remove it.

---

# 73. AI Agent Evaluation — Domain Icons

For each domain icon:

### Semantic Test

Does the geometry express the documented meaning?

### Boundary Test

Could it accidentally imply a stronger concept?

Examples:

- Validation must not look like Trust.
- Evidence must not look like Verification.
- Authority must not look like Ownership.
- Receipt must not look like Certification.

### Family Test

Does it feel like the same system?

### Scale Test

Does it survive at intended size?

All must PASS.

---

# 74. Optical Consistency Rules

The Agent SHALL correct optically, not only mathematically.

Check:

- perceived center;
- visual weight;
- diagonal overshoot;
- circle/curve overshoot;
- internal void sizes;
- stroke convergence;
- Blue accent mass.

Two icons with identical numerical bounds may still look mismatched.

Optical consistency wins.

---

# 75. Complexity Budget

At 24 px:

Preferred:

- one primary silhouette;
- maximum 2–3 interior concepts;
- minimal intersections.

Avoid:

- multiple nested boxes;
- tiny dots;
- micro-text;
- 5+ independent elements.

Domain icon detail may increase at 40/48 px.

---

# 76. Blue Mass Budget

For ordinary domain icons in two-tone mode:

Target blue area:

> generally **10–30% of visible icon mass**

unless the icon is a Brand Motif or active/selected state.

Functional icons should generally have:

> **0% Blue by default**

and inherit color from context.

This preserves Brand ratio discipline.

---

# 77. Shape Repetition Rule

Do not paste Motif A or Motif B into every icon.

The system is derived from visual grammar, not clip-art repetition.

A successful Unfict icon family should remain recognizable even when only some icons contain literal motif fragments.

---

# 78. Familiarity Rule

The more universal the action:

> the less radical the customization.

The more Unfict-specific the concept:

> the more proprietary the geometry may become.

```text
minimal customization

subtle customization

        ↓

Digital Link
domain-specific
moderate customization

        ↓

strong customization

        ↓

```

# 99. Council Review Questions

The Council should ask:

1. Does this look unmistakably Unfict without the logo?
2. Are universal actions still universal?
3. Does the system reduce rather than add visual noise?
4. Can the icons survive a dense enterprise interface?
5. Do the domain icons express Unfict semantics without overclaiming?
6. Does Blue remain scarce and meaningful?
7. Can the family scale across website, product, developers, diagrams, and host-native contexts?
8. Are icons usable at 16/20/24 px?
9. Is the system recognizable in monochrome?
10. Would a future designer be able to add an icon without stylistic drift?

---

# 100. Initial Generation Scope Recommendation

Do NOT generate hundreds of icons.

Recommended first cycle:

```text
6 Brand Motifs
12 Pilot Icons
then, after approval:
23 Functional Icons
24 Domain Icons
```

The intent is to establish a strong grammar before scale.

The system can later grow by governed need.

---

# 101. Expansion Protocol

When a new icon is requested:

1. define semantic name;
2. define exact meaning;
3. define `does_not_mean`;
4. list primary use cases;
5. list avoid cases;
6. classify layer;
7. identify familiarity requirement;
8. select minimal Unfict signature;
9. generate 24 px master;
10. test minimum size;
11. test monochrome;
12. add semantic metadata;
13. run governance tests;
14. publish only after review.

No “draw first, define later.”

# 103. Relationship to Brand Motifs on Photography

Photography and iconography serve different Jobs.

Photography:

> human consequence / Reality / emotion

Iconography:

> structure / semantics / recognition

A full-bleed Human Reality section should generally use **fewer icons**, not more.

Do not overlay large decorative motifs on people’s faces or products merely to increase branding.

---

# 104. Relationship to Typography

Icons support typography.

They do not replace it.

Unfict’s primary Brand authority still comes from:

- exact language;
- IBM Plex Sans;
- IBM Plex Mono where appropriate;
- whitespace;
- disciplined layout;
- restrained Blue.

The icon system is a signature layer, not the entire identity.

---

# 105. Relationship to Motion

Motion may strengthen:

- route;
- resolver;
- loading;
- state transition;
- before/after continuity.

Motion SHALL explain something.

Do not animate icons solely because motion is available.

---

# 106. Relationship to Future Themes

If the product later gains:

- additional themes;
- dark mode;
- host-native skins;

the icon geometry should remain stable.

Adapt through tokens, not icon redesign.

---

# 107. Intellectual / Design Originality Rule

The functional set may follow universal conventions but should be independently drawn.

The domain/motif set should be original to Unfict.

The Agent SHALL avoid substantially reproducing distinctive third-party icon designs.

The goal is:

> **familiar semantics, original geometry.**

---

# 108. Definition of Success

The system succeeds when:

- a Search icon still looks like Search;
- a Resolver icon looks proprietary and meaningful;
- the two can coexist naturally;
- the interface feels unmistakably Unfict without becoming ornamented;
- Blue remains meaningful;
- domain diagrams gain a coherent visual vocabulary;
- unfamiliar concepts remain explainable;
- designers and AI Agents can extend the system without guessing.

---

# 109. Closing Doctrine

> **The logo establishes identity. The icon system extends its character.**

> **Brand motifs may be abstract. Functional icons must remain familiar. Domain icons may become proprietary where semantics permit.**

> **Use the smallest amount of Unfict character necessary to make the system recognizably ours.**

> **Do not decorate what should communicate.**

> **Do not simplify semantics by strengthening them visually.**

> **Do not make every interface element blue.**

> **Do not paste the logo into every icon.**

> **One coherent visual grammar is stronger than fifty clever symbols.**
