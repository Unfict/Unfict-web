---

# 0. Executive Proposition

The Unfict Web interface system SHALL be extracted from coherent approved experiences.

It SHALL NOT be created by independently styling isolated widgets and later assembling them into pages.

The governing creative rule is:

> **DESIGN THE WHOLE → ACCEPT THE WHOLE → EXTRACT THE REUSABLE SYSTEM**

The governing implementation rule remains:

> **FOUNDATIONS → PRIMITIVES → COMPONENTS → PATTERNS → SECTIONS → SHELLS → ARCHETYPES → COMPOSITIONS**

These are not contradictory.

They describe two opposite but complementary directions:

```text
CREATIVE DISCOVERY
COMPOSITION
    ↓
SECTIONS
    ↓
PATTERNS
    ↓
COMPONENTS
    ↓
PRIMITIVES
    ↓
FOUNDATIONS

IMPLEMENTATION COMPOSITION
FOUNDATIONS
    ↓
PRIMITIVES
    ↓
COMPONENTS
    ↓
PATTERNS
    ↓
SECTIONS
    ↓
SHELLS
    ↓
ARCHETYPES
    ↓
COMPOSITION
```

Canonical doctrine:

> **Design flows top-down. Implementation composes bottom-up.**

---

# 1. Why This Protocol Exists

A reusable design system can fail creatively even when it is technically consistent.

If Header, Hero, CTA, Article, Footer, Form, FAQ, and other elements are each designed in isolation, every element may look individually competent while the total experience lacks:

- visual rhythm;
- composition tension;
- hierarchy;
- pacing;
- recognizable brand character;
- intentional whitespace;
- relationship between imagery and type;
- system-level contrast;
- memorable identity.

Unfict therefore treats the complete page experience as the primary creative evidence.

Reusable owners are discovered and normalized **after** the visual language has been demonstrated in context.

This protocol protects against two opposite failures:

```text
FAILURE A
isolated component design
→ technically consistent library
→ visually weak pages

FAILURE B
beautiful one-off pages
→ no reusable ownership
→ long-term visual drift
```

The target is:

```text
COHERENT COMPLETE EXPERIENCES
+
DISCIPLINED EXTRACTION
=
REUSABLE UNFICT VISUAL SYSTEM
```

---

# 2. Core Invariant — Whole Before Parts

For creative work:

> **No reusable visual owner SHALL be considered visually final merely because it looks successful in isolation.**

Reusable appearance should ordinarily be established through one or more accepted complete compositions.

Exceptions exist for upstream locked Brand assets and other already-ratified foundations.

---

# 3. Core Invariant — Extraction, Not Imposition

The system SHALL be extracted from successful compositions.

It SHALL NOT force accepted compositions to conform to prematurely invented visual components.

Wrong:

```text
design Hero in isolation
→ force Homepage to use it
→ force GS1 page to use it
→ distort both pages to preserve component purity
```

Correct:

```text
design Homepage and GS1 experiences coherently
→ observe recurring Hero Job
→ compare treatments
→ extract stable contract
→ rebuild both through the owner
→ verify equivalence
```

If extraction damages an accepted composition:

> **the extraction is wrong or incomplete.**

The accepted composition is not automatically wrong.

---

# 4. Core Invariant — Engine Does Not Lead Visual Design

Placeholder engine implementation may exist before final visual design.

It SHALL NOT become creative precedent merely because it was implemented first.

Therefore:

```text
PLACEHOLDER IMPLEMENTATION
≠
VISUAL EVIDENCE
```

Design agents SHALL ignore placeholder aesthetics when creating active Master Compositions.

Implementation agents SHALL preserve placeholder semantics while waiting for approved visual bindings.

---

# 5. Core Invariant — Source Composition Integrity

An accepted Master Composition is evidence of:

- hierarchy;
- pacing;
- whitespace;
- image/text relationship;
- action prominence;
- density;
- sectional transition;
- visual emphasis;
- information rhythm;
- responsive intent where supplied.

Extraction SHALL preserve these relationships.

A component extraction is not successful merely because the extracted element resembles the source when viewed alone.

It must preserve the role that element played in the full composition.

---

# 6. Core Invariant — Minimum Viable Abstraction

Extract the **smallest stable reusable owner** that captures the recurring Job.

Do not generalize prematurely.

Prefer:

```text
one owner with a clear Job
```

over:

```text
one hyper-configurable owner with 28 options
```

The purpose of extraction is consistent meaning and behavior, not maximal abstraction.

---

# 7. Core Invariant — Reuse Is Semantic Before Visual

Two elements that look similar are not necessarily the same owner.

Two elements that solve the same stable Job may be the same owner even if their early visual treatments differ.

Extraction therefore asks in this order:

```text
1. Is the Job the same?
2. Is the semantic role the same?
3. Is the interaction/state model the same?
4. Is the responsive responsibility the same?
5. Is the accessibility responsibility the same?
6. Is the visual grammar sufficiently related?
```

Visual resemblance alone is insufficient.

---

# 8. Core Invariant — No Component Inflation

A visual element SHALL NOT become a reusable owner merely because it exists.

Promotion requires evidence that reuse improves the system.

Possible dispositions are:

```text
REUSABLE OWNER
APPROVED VARIANT
COMPOSITION-LOCAL STRUCTURE
ONE-OFF EXCEPTION
REJECT / REDESIGN
```

One-off structure is legitimate when the Job is genuinely unique.

---

# 9. Core Invariant — No Page-Specific Duplicate Owner

If two page-local elements perform the same governed Job:

```text
HomepageFAQ
GS1Faq
AboutFaq
```

is prohibited when:

```text
FAQ-ITEM-01
```

can own the shared semantics.

Pages may configure an owner.

They do not independently recreate it.

---

# 10. Core Invariant — Extraction Must Be Reversible

A reusable extraction must be capable of reconstructing its accepted source evidence.

Conceptually:

```text
APPROVED COMPOSITION
        ↓ extract
REUSABLE OWNERS
        ↓ compose
RECONSTRUCTED COMPOSITION
        ↓ compare
APPROVED COMPOSITION
```

This is the **Reconstruction Invariant**.

If reconstruction materially diverges without explicit approval, extraction is incomplete.

# PART I — DESIGN EVIDENCE

# 11. Master Composition Set

The initial Unfict Web visual language SHALL be established through a representative composition family.

Initial target set:

```text
COMPOSITION-HOME-01
COMPOSITION-GS1-PILLAR-01
COMPOSITION-ABOUT-01
COMPOSITION-FAQ-01
COMPOSITION-ARTICLE-01
```

These represent materially different interface Jobs:

```text
HOME
acquisition / brand / commercial orientation

GS1
technical pillar / explanatory / diagram-rich

ABOUT
institutional / identity / editorial

FAQ
answer hub / dense information / disclosure

ARTICLE
long-form reading / technical editorial
```

Together they provide enough breadth to distinguish true reusable grammar from page-specific accident.

---

# 12. Family Accumulation Rule

Master Compositions SHALL be designed as a growing family.

Recommended sequence:

```text
HOME
↓
HOME + GS1
↓
HOME + GS1 + ABOUT
↓
+ FAQ
↓
+ ARTICLE
```

Every later composition should be reviewed beside the earlier accepted compositions.

The goal is not visual sameness.

The goal is recognizable shared authorship.

---

# 13. Complete Composition Evidence

A composition used for extraction SHOULD include, where applicable:

- desktop reference;
- tablet reference;
- mobile reference;
- interaction states;
- navigation states;
- expanded/collapsed states;
- form states;
- article/reading states;
- imagery treatment;
- approved content;
- relevant accessibility notes.

Extraction SHALL NOT invent missing responsive or interaction behavior silently.

Missing evidence remains unresolved.

---

# 14. Evidence Source Priority

For extraction, use evidence in this order:

```text
1. Chair-approved active Unfict composition
2. Chair-approved active component/reference render
3. Active design mandate with explicit accepted visual output
4. Accepted legacy Zyppi composition permitted as structural evidence
5. Figma/Stitch/export artifact tied to accepted design
6. raw generated design code
7. agent interpretation
```

Raw design-generation code is implementation/reference material, not visual authority by itself.

---

# 15. Legacy Design Evidence

Zyppi-era visual work may provide:

- structural evidence;
- composition evidence;
- recurrence evidence;
- responsive clues;
- layout relationships.

It SHALL NOT automatically establish final active Unfict appearance.

When legacy evidence is used:

```text
source:
LEGACY

active visual status:
must remain explicitly tracked
```

Brand-specific Zyppi marks, wordmarks, labels, and active brand expressions shall not be inherited as Unfict final identity.

---

# 16. Evidence Capture Package

Before extraction begins, create or identify an evidence package containing:

```text
Composition ID
Source design link/file
Approved screenshot/render
Viewport
Approval status
Content version
Brand version
Relevant mandate
Notes on known exceptions
Known responsive states
Known accessibility constraints
```

An extraction without traceable source evidence cannot be promoted to `APPROVED`.

# PART II — EXTRACTION PHASES

# 17. Phase 0 — Authority Check

Before extraction:

1. identify the composition;
2. confirm it is accepted for extraction;
3. identify Brand authority;
4. identify ZyUX authority;
5. identify content authority;
6. identify the current Interface Registry;
7. identify existing owners that may already satisfy observed Jobs.

Do not begin by drawing boxes around visual fragments.

Begin by understanding the experience.

---

# 18. Phase 1 — Composition Reading

Read the composition as a whole.

Record:

```text
Primary Job
Primary visitor question
Primary action
Secondary actions
Explanation sequence
Visual peak
Quiet zones
Density changes
Image role
Technical-depth role
Beginning / middle / end rhythm
```

This establishes why each visual region exists.

---

# 19. Phase 2 — Structural Segmentation

Only after reading the whole, identify major composition regions.

Examples:

```text
global navigation
hero
problem framing
concept model
reassurance
FAQ
final CTA
footer
```

Segmentation is descriptive.

It does not yet create reusable owners.

---

# 20. Phase 3 — Job Annotation

Every candidate region SHALL be annotated by Job.

Example:

Wrong:

```text
"blue box with icon"
```

Correct:

```text
"provide one optional deeper path without competing with the primary CTA"
```

The Job determines reuse.

The appearance provides evidence.

---

# 21. Phase 4 — Registry Match

For each annotated Job:

```text
SEARCH CURRENT REGISTRY
```

Possible result:

```text
A. existing governed owner fits exactly
B. existing owner may fit with approved variant
C. existing proposed owner matches
D. no suitable owner exists
E. visual element is composition-local and should not become an owner
```

Do not create a new ID before this step.

---

# 22. Phase 5 — Cross-Composition Comparison

Candidate reusable owners should be compared across all relevant accepted compositions.

Use a comparison matrix.

Example:

| Question | Homepage | GS1 | About | FAQ | Article |
|---|---|---|---|---|---|
| Same Job? | Yes | Yes | No | Yes | Maybe |
| Same action hierarchy? | Yes | Yes | — | Yes | Different |
| Same slot needs? | Similar | Similar | — | Similar | Different |
| Same responsive responsibility? | Yes | Yes | — | Yes | Unknown |
| Same visual grammar? | Yes | Similar | — | Yes | Different |

The matrix prevents false reuse based on one page.

---

# 23. Phase 6 — Classification

Every extracted item must be classified correctly.

Use this hierarchy.

## Foundation

A system value or rule that should not be re-decided per owner.

Examples:

```text
color role
spacing token
content width
border
radius
focus
motion
```

## Primitive

Small atomic interaction/presentation element.

Examples:

```text
button
text link
input
divider
inline code
```

## Component

Reusable functional unit composed from primitives.

Examples:

```text
FAQ item
form field
article metadata
global header
```

## Pattern

Recurring composition solving a user Job.

Examples:

```text
Final CTA
Concept Flow
Related Reading
Hero Action
```

## Section

Reusable page-level composition unit.

Examples:

```text
FAQ Category
Conceptual Model
Human Reality Hero
```

## Navigation / Shell

Persistent structural framing.

Examples:

```text
Global Header
Mobile Nav
Public Web Shell
Article Shell
```

## Archetype

Recurring page Job model.

## Composition-Local

Legitimate structure that should remain owned by one composition.

Do not force composition-local structures into the Registry merely for completeness.

---

# 24. Classification Test

Ask:

```text
Would this element still have a stable Job if removed from this exact page?
```

If no:

> likely composition-local.

If yes, then ask:

```text
At what smallest layer can that Job be owned without losing meaning?
```

Choose that layer.

---

# 25. Phase 7 — Recurrence Test

A candidate should normally have:

```text
at least two credible expected uses
```

before being promoted as reusable.

Exceptions:

- global Header;
- global Footer;
- Shell;
- accessibility infrastructure;
- Brand-locked primitives;
- obvious infrastructural owners required by architecture.

A second visual occurrence is useful evidence, but not mechanically required where the system Job is inherently global.

---

# 26. Phase 8 — Semantic Contract Extraction

Extract the stable semantic contract before extracting CSS.

Record:

```text
ID
Name
Job
Domain
Allowed surfaces
Required slots
Optional slots
Action hierarchy
States
Variants
Prohibited uses
Dependencies
```

The semantic contract is the stable owner identity.

---

# 27. Phase 9 — Content Slot Extraction

Derive slots from accepted composition evidence.

Do not invent excessive flexibility.

Example:

```yaml
id: PATTERN-FINAL-CTA-01

slots:
  heading:
    required: true
  body:
    required: false
  primaryAction:
    required: true
  secondaryAction:
    required: false
```

Do not automatically add:

```text
badge
image
testimonial
stats
three-card list
video
```

because they might be useful someday.

Slots reflect demonstrated legitimate Jobs.

---

# 28. Slot Boundaries

Each slot SHOULD define relevant constraints.

Possible constraints:

```text
required / optional
minimum / maximum items
expected semantic element
maximum action count
allowed content type
whether rich text is permitted
whether media is permitted
whether icon is permitted
```

Do not encode arbitrary character counts unless content/design evidence proves they are necessary.

---

# 29. Slot Overflow Rule

If approved content does not fit:

```text
do not shrink typography
do not truncate silently
do not rewrite authority-controlled copy
do not overflow mobile
```

Instead:

```text
adjust composition
or
raise Pattern Gap
or
revise slot contract through authority
```

Content is not subordinate to template convenience.

---

# 30. Phase 10 — Visual Contract Extraction

Only after semantics are stable, extract visual behavior.

Record:

```text
surface
foreground
accent role
type hierarchy
alignment
spacing relationships
container behavior
border/radius behavior
image treatment
icon relationship
density
visual emphasis
transition to adjacent sections
```

Prefer relationships over isolated pixel values during early extraction.

Example:

Better:

```text
heading-to-body gap is tighter than body-to-actions gap
```

than prematurely declaring:

```text
17px / 29px
```

before system normalization.

---

# 31. Phase 11 — Foundation Candidate Extraction

Repeated values and relationships across accepted compositions may become foundation candidates.

Examples:

```text
spacing rhythm
content widths
section padding
type scale
grid gutters
image ratios
breakpoint behavior
```

Do not derive a token from a single accidental measurement.

Look for recurrence and compositional purpose.

---

# 32. Foundation Normalization

When several accepted values are close:

```text
94px
96px
98px
```

do not automatically preserve all three.

Determine whether they represent:

```text
one intended rhythm
or
three distinct Jobs
```

Then normalize deliberately.

Normalization SHALL preserve the visual character of the accepted compositions.

---

# 33. No False Mathematical Purity

The system does not require every value to fit a perfect geometric scale.

Optical correction is legitimate.

A mathematically elegant token system that weakens the accepted composition is not preferred over a slightly irregular but purposeful system.

Record exceptions.

Do not hide them.

---

# 34. Phase 12 — Responsive Contract Extraction

Responsive behavior belongs to the reusable owner.

Extract:

```text
desktop layout
tablet transition
mobile order
minimum viable width
wrapping
stacking
image crop
overflow
interaction changes
visibility changes
```

Do not infer that mobile is merely desktop stacked vertically.

Mobile should preserve:

```text
Job
meaning
action priority
required explanation
```

while reducing unnecessary breadth.

---

# 35. Responsive Evidence Gap

If only desktop evidence exists:

```text
responsiveStatus: UNRESOLVED
```

Do not silently promote guessed mobile behavior to final owner authority.

A placeholder engine may provide safe semantic stacking while the final design remains unresolved.

---

# 36. Phase 13 — Accessibility Contract Extraction

Accessibility is part of the owner.

Record where applicable:

```text
semantic HTML
accessible name
keyboard behavior
focus order
focus-visible treatment
expanded/collapsed state
screen-reader behavior
touch target
contrast
zoom/reflow
reduced motion
text equivalent for diagrams
status not color-only
```

An extraction that reproduces appearance but loses accessibility fails.

---

# 37. Phase 14 — State Contract Extraction

Interactive owners SHALL define applicable states.

Possible states:

```text
default
hover
focus-visible
active
selected
expanded
collapsed
disabled
loading
error
success
empty
```

Not every owner needs every state.

Do not generate states merely to make a component library look comprehensive.

---

# 38. Phase 15 — Variant Decision

Variants require a real difference in Job or stable use context.

Ask:

```text
Does this variation change the Job?
Does it change action hierarchy?
Does it change required slots?
Does it change semantic emphasis?
Does it recur?
```

If no:

> treat it as styling/state/composition, not a new variant.

---

# 39. Variant vs New Owner

Use a variant when:

- semantic Job is unchanged;
- slot model is substantially shared;
- accessibility responsibility is shared;
- responsive behavior is fundamentally shared.

Create a new owner when:

- the Job changes materially;
- semantic responsibilities diverge;
- required slots differ enough to distort the original;
- interaction model changes;
- accessibility model changes.

---

# 40. No Page-Named Variants

Avoid:

```text
hero-home
hero-gs1
hero-about
cta-home
cta-faq
```

Prefer Job names:

```text
HeroAction
HeroEditorial
FinalCta
```

A page name is evidence location, not semantic identity.

---

# PART III — EXTRACTION DISPOSITIONS

# 41. Disposition A — Reuse Existing Owner

Use when the existing Registry contract already fits.

Action:

```text
record source composition as additional evidence
do not create new owner
```

---

# 42. Disposition B — Extend with Approved Variant

Use when the Job is stable but a recurring legitimate specialization exists.

Action:

```text
define variant
identify evidence
update Registry
verify all existing uses
```

---

# 43. Disposition C — Create New Reusable Owner

Use only when:

1. no existing owner fits;
2. the Job is stable;
3. reuse is credible;
4. semantic boundaries are clear;
5. responsive responsibility is understood or explicitly unresolved;
6. accessibility responsibility is understood;
7. extraction improves consistency.

Action:

```text
create Pattern Gap
obtain disposition
register owner
extract contract
```

---

# 44. Disposition D — Composition-Local Structure

Use when the treatment is legitimate but unique.

The structure remains inside the composition.

It SHALL NOT be copied to another page without re-evaluation.

---

# 45. Disposition E — Reject / Redesign

Use when:

- the element conflicts with Brand;
- conflicts with ZyUX;
- strengthens semantics improperly;
- creates capability leakage;
- introduces visual dialect;
- duplicates an existing owner badly;
- harms accessibility;
- exists only as decoration without a Job.

---

# PART IV — RECONSTRUCTION & EQUIVALENCE

# 46. Reconstruction Gate

After extraction, rebuild the accepted source composition using the extracted owners.

This is mandatory before visual promotion to `APPROVED` where technically feasible.

---

# 47. Equivalence Dimensions

Compare:

```text
hierarchy
composition
spacing rhythm
type hierarchy
image role
action priority
section pacing
responsive behavior
interaction behavior
content integrity
accessibility
```

Pixel identity is not always required.

Perceptual and semantic equivalence is required.

---

# 48. Allowed Reconstruction Differences

Differences may be accepted when they are:

- normalization of accidental values;
- accessibility corrections;
- optical corrections;
- repository-native technical improvements;
- explicit Brand migration;
- explicitly approved simplification.

They must be documented.

---

# 49. Prohibited Reconstruction Drift

Extraction SHALL NOT accidentally introduce:

- tighter or looser page density;
- different action priority;
- extra cardification;
- more Blue;
- new shadows;
- new radius language;
- new navigation;
- altered image role;
- altered reading width;
- changed content order;
- weakened mobile hierarchy.

---

# 50. Multi-Source Equivalence

When one owner is extracted from several accepted compositions, it must support all legitimate source uses without degrading one source to favor another.

If this cannot be achieved cleanly:

```text
reconsider abstraction boundary
```

Possible result:

- variant;
- separate owner;
- composition-local exception.

---

# 51. Visual Regression Baseline

Once an extracted owner is approved and implemented, create deterministic reference renders where useful:

```text
desktop
tablet
mobile
interactive states
```

The baseline becomes implementation evidence.

It does not replace the original composition evidence.

# PART V — REGISTRY STATUS TRANSITIONS

# 52. Initial Candidate

A pre-existing semantic owner may begin:

```yaml
semanticStatus: GOVERNED
visualStatus: UNDESIGNED
implementationStatus: NOT_IMPLEMENTED
```

or:

```yaml
semanticStatus: GOVERNED
visualStatus: REFERENCE_PAGE_ACCEPTED
implementationStatus: PLACEHOLDER
```

---

# 53. Extraction Transition

After extraction from accepted composition evidence:

```text
visualStatus:
REFERENCE_PAGE_ACCEPTED
→ CANDIDATE_EXTRACTED
```

Do not jump directly to `FROZEN`.

---

# 54. Approval Transition

After Chair/design-authority acceptance:

```text
visualStatus:
CANDIDATE_EXTRACTED
→ APPROVED
```

---

# 55. Freeze Transition

After:

- implementation exists;
- reconstruction passes;
- responsive/state evidence is sufficient;
- visual regression baseline exists where applicable;

then:

```text
visualStatus:
APPROVED
→ FROZEN
```

---

# 56. Implementation Transition

Engine lifecycle:

```text
NOT_IMPLEMENTED
→ PLACEHOLDER
→ IMPLEMENTED
→ VERIFIED
```

Visual and implementation transitions remain independent.

---

# 57. Semantic Status Protection

Visual redesign SHALL NOT silently redefine the owner Job.

If approved visual evidence proves the semantic contract is wrong:

```text
semantic change requires explicit Registry review
```

Do not hide a semantic change inside CSS or slot additions.

---

# PART VI — CREATIVE AGENT PROTOCOL

# 58. Creative Agent Role

Stitch or another creative agent should operate as:

> **Whole-Composition Design Agent**

during Master Composition creation.

It should not begin from a library of unresolved placeholder visuals.

It should receive:

- Brand authority;
- ZyUX/Web experience authority;
- approved content;
- prior accepted Master Compositions;
- relevant locked assets;
- current semantic Registry;
- explicit instruction that placeholder aesthetics are non-authoritative.

---

# 59. Creative Input Package

For each Master Composition, provide:

```text
Page Job / archetype
Canonical content
Navigation scope
Brand assets
Relevant prior accepted compositions
Known semantic owners
Known prohibited patterns
Required viewport proofs
Required states
```

Do not overload the creative agent with implementation code unless necessary for a specific constraint.

---

# 60. Creative Continuity Rule

When designing composition N:

```text
show accepted compositions 1…N-1
```

The agent should preserve family resemblance through:

- composition rhythm;
- density;
- typography behavior;
- image behavior;
- action hierarchy;
- section transitions;
- technical diagram language.

It may introduce new visual solutions when the Job genuinely requires them.

---

# 61. Creative Freedom Boundary

The Registry defines semantic owners and known Jobs.

It SHALL NOT force an unresolved visual treatment.

If:

```text
visualStatus != APPROVED/FROZEN
```

the creative agent may explore the visual treatment within higher authority.

If:

```text
visualStatus = APPROVED/FROZEN
```

the owner should normally be reused.

---

# 62. No Placeholder Contamination

Do not show neutral placeholder components as if they were visual references.

If engine screenshots are included for functional reasons, label them:

```text
STRUCTURAL PLACEHOLDER — NOT VISUAL AUTHORITY
```

---

# PART VII — ENGINEERING AGENT PROTOCOL

# 63. Jules Extraction Role

Jules is responsible for repository-native implementation and evidence.

Jules may:

- inspect accepted composition exports;
- identify existing runtime owners;
- implement extracted contracts;
- refactor duplicates into governed owners;
- build visual-regression fixtures;
- run accessibility checks;
- provide evidence receipts.

Jules SHALL NOT independently decide unresolved visual design.

---

# 64. Implementation Source Package

Before implementing an extracted owner, Jules should receive local repository evidence containing:

```text
Registry record
approved composition screenshot/export
component extraction specification
required responsive/state references
asset references
content-slot contract
accessibility contract
```

External design links alone are insufficient if Jules cannot access them.

---

# 65. Raw Design Code Rule

Stitch/Figma-exported code may inform:

- hierarchy;
- geometry;
- spacing;
- responsive clues.

It SHALL NOT automatically become production implementation.

Jules should implement repository-native owners.

---

# 66. Placeholder Replacement Rule

When a placeholder runtime owner already exists:

```text
retain semantic API
retain owner ID
retain intended runtime path where practical
replace neutral visual implementation
update Registry implementation status
add regression evidence
```

Do not create `ComponentFinal`, `ComponentNew`, or page-specific duplicates.

---

# 67. API Change Escalation

If approved design cannot be implemented without changing the existing semantic component API:

Jules SHALL report:

```text
API MISMATCH
current contract
required contract
reason
affected consumers
recommended migration
```

Do not silently broaden props until every possible visual can fit.

# PART IX — CONFLICT HANDLING

# 71. Conflicting Accepted Compositions

Two accepted compositions may contain conflicting treatments.

Do not average them automatically.

Determine whether the difference is:

```text
different Job
different variant
different state
legacy drift
brand migration
accidental inconsistency
```

Then resolve deliberately.

---

# 72. Conflict Dispositions

Possible outcomes:

```text
A. one treatment becomes canonical
B. two legitimate variants
C. separate owners
D. composition-local exception
E. both redesigned
```

Record the reason.

---

# 73. Brand Conflict

If accepted composition evidence conflicts with current Brand authority:

> Brand authority wins prospectively.

The composition may require migration.

Do not preserve historical appearance merely to satisfy screenshot equivalence.

---

# 74. ZyUX / Semantic Conflict

If a visually accepted treatment strengthens, weakens, or exposes meaning beyond current ZyUX/content authority:

> semantic authority wins.

Visual acceptance cannot authorize false product meaning.

# PART XI — QUALITY GATES

# 80. Extraction Quality Gate

An extracted owner cannot be visually approved until:

- its Job is clear;
- its layer is correct;
- existing owners were reviewed;
- slots are bounded;
- variant decision is justified;
- responsive responsibility is known or explicitly unresolved;
- accessibility responsibility is known;
- source evidence is traceable;
- reconstruction is acceptable;
- Registry status is updated.

---

# 81. Anti-Over-Abstraction Gate

Fail extraction if the owner:

- requires excessive boolean props;
- contains mutually unrelated Jobs;
- exists only to reduce file count;
- needs page-name switches;
- has dozens of visual options;
- weakens composition quality to preserve API purity.

---

# 82. Anti-Under-Abstraction Gate

Fail extraction if:

- equivalent Jobs are duplicated across pages;
- state behavior differs accidentally;
- responsive behavior is independently reimplemented;
- accessibility responsibility has multiple owners;
- identical visual semantics depend on local CSS.

---

```text
restricted radius
no decorative shadows
no visual proof theater
no generic SaaS card inflation
```

# 84. ZyUX Gate

Review:

```text

minimum useful surface

```

A frozen owner may be re-extracted when:

- responsive evidence exposes an incomplete contract;

Re-extraction requires explicit review.

Do not leave parallel active dialects indefinitely.

Creative agents SHALL NOT:

- redesign approved frozen owners without authority;
- introduce new brand colors;
- invent capability exposure;
- create visual proof theater;
- optimize pages around implementation convenience;
- force every region into an existing component;
- create novelty merely to avoid reuse.

# 93. Engineering Agent Prohibitions

Implementation agents SHALL NOT:

- infer final visuals from placeholder code;
- create local page-specific copies of governed owners;
- silently broaden component APIs;
- invent unresolved responsive behavior as final;
- change approved content to fit slots;
- normalize away meaningful visual distinctions;
- update visual baselines blindly;
- treat design export code as production authority.

# 94. Registry Prohibitions

Registry updates SHALL NOT:

- mark a visual owner `APPROVED` because code exists;
- mark implementation `VERIFIED` because a screenshot looks right;

- use `PLACEHOLDER` as a visual-status value;
- hide unresolved evidence.

# 101. Final Canonical Summary

The protocol reduces to twelve rules:

1. **Design complete experiences before finalizing reusable visuals.**
2. **Treat accepted compositions as primary creative evidence.**
3. **Extract by recurring Job, not by superficial appearance.**
4. **Search the Registry before creating an owner.**
5. **Use the smallest stable abstraction that preserves meaning.**
6. **Do not promote every visual fragment into the system.**
7. **Derive slots, states, responsive behavior, and accessibility from evidence.**
8. **Normalize foundations only after recurrence becomes visible.**
9. **Reconstruct accepted compositions from extracted owners.**
10. **If reconstruction degrades the accepted design, revisit the extraction.**
11. **Keep semantic, visual, and implementation status independent.**
12. **Let Creative discover top-down while Engineering composes bottom-up.**

The resulting operating principle is:

> **The page proves the language. The extraction captures the language. The Registry governs the language. The engine reproduces the language.**
