# 0. Executive Proposition

Unfict SHALL maintain one governed Web interface system that preserves visual identity, interaction consistency, semantic accuracy, accessibility, and implementation reuse across public Web surfaces.

The governing proposition remains:

> **One visual grammar. Many legitimate compositions.**

This system adds a second governing distinction:

> **Design flows top-down. Implementation composes bottom-up.**

The creative system SHALL therefore begin from coherent whole-page compositions, not from isolated component styling.

The implementation system MAY proceed in parallel by establishing stable semantic owners, content-slot contracts, runtime interfaces, accessibility behavior, responsive contracts, registries, tests, and deliberately neutral placeholders before final visual designs are approved.

The full operating model is:

```text
UPSTREAM AUTHORITY
Brand + ZyUX + Content + Current Product Truth
                │
                ▼
        MASTER COMPOSITIONS
 coherent pages designed as a family
                │
                ▼
        VISUAL ACCEPTANCE
                │
                ▼
       REUSABLE EXTRACTION
 sections → patterns → components → primitives
                │
                ▼
         NORMALIZATION
 tokens / spacing / widths / states / variants
                │
                ▼
        APPROVED VISUAL OWNERS
                │
                ▼
       PRODUCTION IMPLEMENTATION

PARALLEL ENGINE TRACK
semantic owner → registry → placeholder runtime → tests
                │
                └───────────────┐
                                ▼
                    approved design binding
                                │
                                ▼
                     final production surface
```

The objective is not to create a catalogue of individually attractive components.

The objective is to create a Web experience whose whole-page compositions feel unmistakably Unfict, and then extract that visual language into stable reusable owners without degrading the approved compositions.

# 1. Why This Construct Exists

Unfict's public Web surface must not become either of the following:

1. a collection of independently styled pages that merely resemble each other; or
2. a rigid component catalogue whose isolated pieces are technically consistent but whose assembled pages lack visual coherence.

Both failure modes are unacceptable.

The first produces drift.

The second produces generic design-system output.

Unfict therefore requires a system that protects both:

```text
CREATIVE COHERENCE
+
IMPLEMENTATION CONSISTENCY
```

The system SHALL support reusable:

- foundations and tokens;
- primitives;
- components;
- patterns;
- sections;
- navigation systems;
- shells;
- page archetypes;
- approved compositions;
- state models;
- responsive behaviors;
- accessibility contracts;
- content-slot contracts;
- runtime ownership;
- implementation status;
- visual evidence;
- placeholder substitution;
- visual-regression ownership.

# 2. Foundational Doctrine — Whole Before Parts

The Web design process SHALL begin from complete or meaningfully complete compositions.

A reusable component SHALL NOT be visually frozen merely because its semantic Job is known.

Where practical, visual language should emerge from representative page compositions that exercise different legitimate Web Jobs.

The preferred creative sequence is:

```text
1. Design complete representative compositions.
2. Review those compositions together as one family.
3. Correct the shared visual language at composition level.
4. Accept the compositions as visual evidence.
5. Identify repeated Jobs and recurring treatments.
6. Extract reusable owners.
7. Normalize shared rules.
8. Rebuild the reference compositions using extracted owners.
9. Confirm visual equivalence.
10. Promote reusable owners only after the extraction survives this test.
```

This principle exists because isolated component design can optimize individual pieces while damaging page-level rhythm, hierarchy, pacing, proportion, and brand character.

---

# 3. Foundational Doctrine — Design Top-Down / Implementation Bottom-Up

The system SHALL explicitly distinguish creative direction from implementation composition.

## 3.1 Creative Flow

Creative design normally flows:

```text
Approved Composition
        ↓
Section
        ↓
Pattern
        ↓
Component
        ↓
Primitive
        ↓
Normalized Foundation
```

This is a process of extraction.

## 3.2 Implementation Flow

Production implementation normally composes:

```text
Foundation
        ↓
Primitive
        ↓
Component
        ↓
Pattern
        ↓
Section
        ↓
Shell
        ↓
Archetype
        ↓
Page Composition
```

This is a process of assembly.

The two flows are intentionally opposite.

They SHALL NOT be confused.

---

# 4. Foundational Doctrine — Stable Owner Before Final Artwork

A reusable interface owner may exist before its final visual design is approved.

The system MAY establish early:

- canonical ID;
- semantic Job;
- layer;
- domain;
- content slots;
- required / optional content;
- state contract;
- accessibility contract;
- responsive obligations;
- runtime owner;
- component API;
- test harness;
- placeholder implementation.

This does NOT authorize final visual styling.

The governing principle is:

> **The engine may become structurally real before the visual treatment is final.**

This is the same separation used by the Unfict icon system:

```text
stable semantic identity + runtime contract
                │
                ▼
      temporary implementation
                │
                ▼
        approved visual asset
                │
                ▼
      replace without consumer drift
```

# 5. Placeholder Interface Invariant

Where a reusable owner is semantically defined but not visually approved, the implementation MAY use a neutral placeholder owner.

A placeholder SHALL be:

- structurally representative;
- semantically accurate;
- accessible;
- responsive enough to exercise the contract;
- deliberately visually neutral;
- machine-identifiable as placeholder state;
- replaceable without consumer-code changes.

A placeholder SHALL NOT:

- invent the final layout;
- invent a final spacing rhythm;
- invent final radius, surface, image, or decoration treatment;
- be presented as approved Unfict visual design;
- create visual precedent merely because it exists in code.

The replacement invariant is:

> **Binding an approved visual design to an existing owner SHALL NOT require page consumers to change semantic owner, content model, import path, or public component API unless the approved design proves the prior semantic contract itself was wrong.**

---

# 6. Single Visual Pattern Owner

Every recurring Unfict Web interface Job SHALL have one governed design-system owner.

Pages MAY compose or configure that owner.

They SHALL NOT independently reproduce its:

- visual semantics;
- behavioral semantics;
- responsive semantics;
- accessibility semantics;
- state semantics;
- content-slot semantics.

Example:

```text
FAQ-ITEM-01
     │
     ├── Homepage FAQ
     ├── FAQ Page
     └── GS1 Page
```

Not:

```text
HomepageFaq
Gs1Accordion
FaqBox
AboutQuestion
```

when the Job is the same.

This invariant is mandatory.

---

# 7. Reuse Before Invention

Before creating a new reusable owner, an authorized designer or implementation agent SHALL:

1. inspect the governed interface registry;
2. identify whether an existing owner satisfies the Job;
3. reuse it when it does;
4. use an approved variant where the underlying Job is legitimately different;
5. record a Pattern Gap when no owner fits.

No agent SHALL silently invent a parallel owner.

---

# 8. Composition Is Not Redesign

A page may combine governed owners in a new composition.

That does not authorize the page to change:

- typography system;
- color roles;
- button treatment;
- FAQ behavior;
- navigation semantics;
- image doctrine;
- accessibility behavior;
- global responsive behavior;
- icon semantics;
- component state semantics.

New composition is legitimate.

Local redesign is not implied.

---

# 9. Approved Composition Has Evidentiary Priority During Extraction

Once a complete composition has been explicitly accepted as a visual reference, extraction SHALL preserve that composition unless higher authority requires change.

The system SHALL NOT retroactively distort an accepted page merely to make extraction easier.

The extraction test is:

> **Can the accepted composition be reproduced through the extracted reusable owner without material visual or semantic degradation?**

If no:

- the extraction may be wrong;
- the proposed owner may be too broad;
- the proposed owner may need an approved variant;
- the element may legitimately remain composition-specific.

Do not force reuse where the Job is not actually shared.

---

# 10. Design Availability ≠ Product Availability

The existence of a Web component, pattern, section, icon, navigation style, form control, or template does not authorize public exposure of a capability.

Visibility remains governed by:

- current product truth;
- content authority;
- ZyUX disclosure rules;
- GTM scope;
- authorization;
- current implementation state.

A design-system owner is a reusable visual/interaction construct, not a product roadmap promise.

---

# 11. No Agent-Specific Visual Dialect

Stitch, Jules, Figma workflows, and future authorized AI agents SHALL NOT create separate visual dialects.

Their roles differ:

```text
STITCH / DESIGN AGENT
whole-composition exploration and controlled visual invention

JULES / IMPLEMENTATION AGENT
repository-native contracts, extraction, implementation, tests, accessibility, visual fidelity
```

Both operate under the same interface system.

A design that cannot be mapped to governed owners after extraction is not production-ready.

An implementation that cannot identify its owner is incomplete.

# 34. Pattern Promotion Rule

A design element should become a reusable owner when:

1. it solves a recurring Job;
2. reuse is likely across more than one legitimate surface;
3. its semantics are stable;
4. responsive behavior can be defined;
5. accessibility can be defined;
6. its visual language is consistent with accepted compositions;
7. reuse improves consistency rather than flattening meaningful differences.

Do not promote one-off decoration unnecessarily.

---

# 35. Recurrence Evidence

The default maturity logic SHOULD be:

```text
first occurrence
→ composition-specific / candidate observation

second legitimate recurrence
→ extraction candidate

repeated validated use
→ strong reusable owner

explicit acceptance
→ approved owner

stable implementation + regression coverage
→ frozen / verified owner
```

Global constructs such as Header, Footer, or public shell may be extracted earlier where ownership is already structurally obvious and visual evidence exists.

---

# 36. Design Extraction Protocol

When a composition is visually accepted:

```text
STEP 1
Identify repeated visual Jobs.

STEP 2
Compare them with the current Interface Registry.

STEP 3
Reuse existing owner where semantically equivalent.

STEP 4
If no owner fits, record Pattern Gap.

STEP 5
Determine whether treatment is:
- composition-specific;
- approved variant;
- or genuinely reusable owner.

STEP 6
Extract the smallest stable semantic API.

STEP 7
Bind approved visual behavior to the owner.

STEP 8
Reconstruct the accepted composition using the extracted owner.

STEP 9
Run visual-equivalence review.

STEP 10
Promote status only if composition fidelity is preserved.
```

This workflow SHALL be elaborated by a companion `UNFICT-WEB-DESIGN-EXTRACTION-PROTOCOL-001`.

# 37. Visual Equivalence Gate

A newly extracted owner SHALL pass against its source composition.

Review SHALL include:

- typography;
- geometry;
- spacing;
- alignment;
- image relationship;
- border and surface treatment;
- interactive states;
- mobile ordering;
- accessibility behavior;
- content overflow;
- legitimate semantic differences.

If extraction produces visible degradation, do not approve it merely because the code is more reusable.

---

# 38. Content Slot Contract

Every reusable component, pattern, and section SHALL define content slots where applicable.

Example:

```yaml
id: PATTERN-FINAL-CTA-01
slots:
  eyebrow:
    required: false
  heading:
    required: true
  body:
    required: false
  primaryAction:
    required: true
  secondaryAction:
    required: false
```

Slot contracts protect both design and content semantics.

---

# 39. Slot Overflow Rule

If approved content does not fit a governed slot:

> change composition, revise the owner through authority, or raise Pattern Gap.

Do NOT:

- shrink text below acceptable scale;
- silently truncate;
- rewrite approved copy without content authority;
- overflow mobile;
- create a one-off local component to evade the contract.

Content is authority.

Design adapts.

---

# 40. Component API Stability

Placeholder and final visual implementations SHOULD expose the same semantic consumer API.

Example:

```astro
<FinalCta
  heading="..."
  body="..."
  primaryAction={...}
/>
```

Consumer pages should not need to know whether the runtime owner is:

```text
PLACEHOLDER
or
APPROVED / IMPLEMENTED
```

The status belongs to system metadata.

---

# 41. Placeholder Visual Neutrality

Placeholder components SHALL avoid establishing false creative precedent.

Recommended placeholder treatment:

- inherited typography;
- plain document flow;
- thin neutral border only where useful for debugging boundaries;
- simple structural labels in development-only contexts;
- no novel background color;
- no novel radius;
- no decorative image treatment;
- no Blue merely to make the placeholder feel branded;
- no animation except where required to test behavior.

A placeholder is an engine fixture, not a design proposal.

---

# 42. Placeholder Tracking

The Interface Registry SHALL explicitly identify placeholder implementation state.

The implementation SHOULD support machine-readable discovery of:

- all placeholder owners;
- all approved-but-not-implemented owners;
- all implemented-but-not-visually-approved owners;
- all frozen/verified owners.

Final public-release policy MAY require zero unresolved placeholders for launch-critical surfaces while allowing non-routed future owners to remain unimplemented.

---

# 43. Responsive Contract

Every reusable interactive or compositional owner SHALL define:

- desktop behavior;
- tablet behavior;
- mobile behavior;
- minimum viable width;
- wrapping;
- ordering changes;
- image crop / focal behavior where applicable;
- overflow handling;
- interaction changes;
- touch-target behavior.

Responsive behavior belongs to the owner.

Pages SHALL NOT independently reinterpret it.

---

# 44. Mobile Semantic Preservation

Mobile MAY change:

- stacking;
- spacing;
- visual density;
- image crop;
- disclosure mechanics;
- nonessential decorative complexity.

Mobile SHALL NOT silently change:

- information priority;
- action priority;
- capability visibility;
- required limitations;
- factual meaning.

The governing mobile sequence remains:

```text
PAGE JOB
↓
KEY EXPLANATION
↓
PRIMARY CTA
↓
OPTIONAL DEPTH
```

- Article Experience Is Reading-First;
- Technical Depth Must Be Observable;
- Developer Language Stays Domain-Native;
- Do Not Imply Unfict Replaces Systems of Work;
- Current Capability, Future Depth;
- Status Is Meaning, Not Decoration;
- Color Is Never the Only Meaning;
- Error States Stay Near the Job;
- Distinguish System Failure From Product State;
- Mobile Prioritizes Context;
- Accessibility Is Experience Correctness;
- No Visual Complexity for Its Own Sake.

The successor Brand name is Unfict; substantive ZyUX meaning remains inherited unless separately amended.

# 47. Page-Level Job Before Decorative Completeness

Every visible section, control, visual, CTA, badge, and navigation item consumes cognitive capacity.

For every visible object ask:

> **What visitor Job does this advance?**

If no clear answer exists, remove it or redesign it.

The interface system SHALL NOT encourage component use merely because a component exists.

A component or section marked as a primary action owner SHALL reflect the current visitor Job.

Pages should generally expose one visually dominant primary action within the same decision context.

Secondary actions should remain visually subordinate.

# 61. Pattern Gap Protocol

When no governed owner fits, record:

```text
PATTERN-GAP
```

Required fields:

```text
Page / Surface
Job
Why existing owner cannot satisfy
Closest existing owner
Proposed new owner or variant
Expected reuse
Responsive considerations
Accessibility considerations
Semantic risk
Visual evidence
```

The design authority may decide:

```text
A. Reuse existing owner unchanged
B. Extend existing owner with approved variant
C. Create new owner
D. Approve composition-specific exception
E. Reject proposed UI
```

No agent may silently choose C or D.

---

# 62. Variant Rule

Variants are legitimate only when the underlying Job differs materially or an accepted composition proves a stable recurring need.

Do not create aesthetic variants solely for variety.

Prefer:

```text

ONE global header
ONE global footer
ONE article shell
A SMALL NUMBER of legitimate hero patterns
```

over dozens of stylistic options.

The goal is:

> **constrained composability.**

# 77. Creative / Engineering Handshake

An owner moves from placeholder to production visual implementation through this handshake:

No hidden handoff assumptions.

# 98. System Success Criteria

The Interface System succeeds when:

1. complete pages feel like one coherent Unfict family;
2. repeated Jobs map to one owner;
3. accepted visual language can be extracted without degrading the compositions;
4. pages do not independently invent reusable UI;
5. the engine can operate before final visual approval through neutral placeholders;
6. approved visuals can replace placeholders without consumer-code churn;
7. Brand and ZyUX semantics survive implementation;
8. accessibility is structural;
9. responsive behavior is owned rather than improvised;
10. future agents can determine what exists, what is approved, what is placeholder, and what requires design authority.

# 99. Canonical Working Statements

The system may be summarized by the following statements:

> **One visual grammar. Many legitimate compositions.**

> **Design the experience as a whole before reducing it to parts.**

> **Extract the system from successful compositions; do not force compositions to emerge from prematurely designed parts.**

> **Design flows top-down. Implementation composes bottom-up.**

> **Build stable runtime contracts before final visuals are ready where doing so does not pre-judge the design.**

> **Placeholder implementation is not visual approval.**

> **Every recurring Job has one governed owner.**

> **Reuse before invention.**

> **If no owner fits, record Pattern Gap.**

> **Approved visual replacement should be consumer-code neutral.**
