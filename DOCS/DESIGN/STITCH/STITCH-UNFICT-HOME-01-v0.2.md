# 0. Revision Proposition

Version `0.2` corrects the acquisition-layer complexity of the Homepage.

The previous mandate allowed the Homepage to communicate too close to the level of an expert standards or architecture audience.

The revised governing rule is:

> **The Unfict Homepage SHALL be understandable at technical-complexity level 3–4 out of 10.**

Where:

```text
0  = no domain knowledge required
3  = intelligent general business visitor
4  = manager responsible for a digital/product initiative
6  = manager actively implementing GS1 / connected-product infrastructure
8  = experienced solution architect / GS1 specialist
10 = expert standards consultant / reference-level specialist
```

The Homepage is not documentation.

The Homepage is not a standards seminar.

The Homepage is not a resolver architecture diagram.

The Homepage must first create:

```text
recognition
relevance
emotion
understanding
curiosity
confidence
```

Technical depth remains available — but underneath progressive layers.

---

# 1. New Core Doctrine — Outcome Before Mechanism

The public entry layer SHALL explain:

```text
what changes for the visitor
why that matters
what becomes easier / more durable / more useful
```

before explaining:

```text
what standard is involved
what architecture is used
what resolver behavior exists
what API vocabulary applies
```

Canonical rule:

> **Outcome before mechanism. Meaning before terminology. Relevance before architecture.**

The visitor should not need to know what a resolver is to understand why Unfict matters.

---

# 2. New Core Doctrine — Progressive Complexity

Complexity should increase only when the visitor chooses to go deeper.

Target complexity ladder:

| Experience layer | Target complexity | Communication mode |
|---|---:|---|
| Homepage Hero | 2–3 / 10 | Emotional, intuitive, outcome-led |
| Homepage body | 3–4 / 10 | Plain-language business understanding |
| GS1 / solution pillar | 4–5 / 10 | Standards-aware explanation |
| Capability / operational explanation | 5–6 / 10 | Process and system behavior |
| Developer entry | 6–7 / 10 | Technical vocabulary and examples |
| Developer documentation | 7–8 / 10 | APIs, identifiers, resolver behavior |
| Standards / reference | 9–10 / 10 | Expert architecture and standards detail |

The Homepage SHALL NOT collapse these layers into one page.

# 63. Proposed New Web Invariant — Progressive Complexity

Recommended for later incorporation into the governing Web system:

> **Progressive Complexity Invariant**  
> Public acquisition surfaces SHOULD communicate at approximately level 3–4 on a 0–10 technical-complexity scale, where 0 requires no domain knowledge and 10 assumes expert standards knowledge. Higher-complexity concepts SHALL be progressively disclosed through solution, developer, documentation, and reference layers. A visitor SHALL NOT need GS1, API, resolver, ontology, or architecture expertise to understand Unfict's primary public value proposition.

> Public pages SHALL explain what becomes easier, more durable, more useful, or more understandable before explaining the technical mechanism that enables it.
