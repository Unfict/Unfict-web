# 0. Purpose

This document is the persistent visual and product context that SHALL accompany significant Unfict Web design work in Google Stitch.

It exists to prevent:

- context drift between independently generated screens;
- generic AI-SaaS visual language;
- inconsistent colors, typography, spacing character, imagery, and action hierarchy;
- accidental redefinition of product meaning;
- premature freezing of unresolved component or foundation details;
- creative contamination from neutral engineering placeholders.

This document is deliberately compact enough to reuse across Stitch sessions.

It is **not** a component specification.

It is **not** a page mandate.

It is **not** a CSS implementation contract.

It establishes the stable creative territory within which each page-specific Stitch mandate operates.

# 2. What Unfict Is

Unfict is the continuing platform formerly developed under the Zyppi name.

# 6. Brand Palette — Locked

Use only the governed Unfict corporate palette unless a later authority explicitly adds another value.

```text
White
#FFFFFF

Institutional Gray
#F6F7F9

Deep Ink
#0A0D14

Slate
#596273

Border Gray
#DDE1E7

Unfict Blue
#1965EC
```

Canonical composition principle:

> **White creates the room. Ink establishes authority. Blue identifies Unfict. Nothing else should compete.**

Typical visual balance should remain broadly consistent with:

```text
70–85%  White / Institutional Gray
10–25%  Deep Ink / Slate
2–8%    Unfict Blue
```

These percentages express visual restraint.

They are not pixel quotas.

---

# 7. Unfict Blue — Use with Restraint

Unfict Blue should primarily identify:

- primary actions;
- links;
- active navigation;
- selected diagram emphasis;
- key moments of brand recognition;
- restrained technical emphasis.

Do not flood whole pages with Blue.

Do not use Blue merely because a section feels visually empty.

Do not create additional accent colors to compensate.

---

# 8. Typography — Locked Family

Primary family:

```text
IBM Plex Sans
```

Technical / code family:

```text
IBM Plex Mono
```

The typographic feeling should be:

```text
institutional
modern
neutral
highly legible
controlled
not ornamental
```

Do not introduce:

- display typefaces;
- decorative serifs;
- geometric novelty fonts;
- handwritten fonts;
- a second sans-serif family.

The proprietary Unfict wordmark is artwork.

Do not recreate the wordmark by typesetting the word `unfict`.

# 11. Radius Doctrine

The Brand direction uses restrained radii.

Do not make the site look:

```text
bubble-like
playful
mobile-app rounded
consumer fintech
```

Exact radius token mapping is not frozen in this context.

Stitch may use restrained, low-radius treatment consistently while preserving the institutional character.

---

# 12. Shadow Doctrine

> **No decorative shadows.**

Use borders, contrast, spacing, and surface changes to establish hierarchy.

A shadow should not become the default means of separating UI.

---

# 13. Image Doctrine — Reality First

Preferred imagery:

- real products;
- real labels;
- real packaging;
- real barcodes and QR codes where contextually legitimate;
- real retail, logistics, manufacturing, or product environments;
- documentary human interaction with physical products;
- credible infrastructure contexts;
- restrained environmental photography.

Image tone:

```text
documentary
observational
specific
credible
quiet
```

Avoid:

```text
generic office teams
handshakes
people pointing at dashboards
robot imagery
holograms
AI brains
cyber grids
blockchain cubes
floating data nodes
futuristic tunnels
fake command centers
stock-photo celebration
```

The website should show Reality before abstraction.

# 14. Human Presence

Human imagery may be used where it helps explain:

```text

what physical context is involved
what real-world action is happening
```

Human presence should not become generic workplace decoration.

Avoid staged corporate stock-photo behavior.

# 16. Iconography

Use governed Unfict icon semantics where icons are appropriate.

The visual design should expect the Unfict icon system to exist.

Do not introduce third-party icon-library visual dialects as identity.

Do not over-iconify explanatory content.

Icons are functional or conceptual support, not decoration.

---

# 17. Page Rhythm

The site should feel spacious without becoming empty.

Preferred rhythm:

```text
clear visual opening
strong hierarchy
controlled alternation of explanation and evidence
quiet transitions
few simultaneous focal points
clear ending action
```

Avoid a repetitive pattern of:

```text
hero
three cards
three cards
logo strip
three cards
CTA card
```

The page should feel composed as a whole.

---

# 18. Card Doctrine

Cards are allowed when the Job needs a bounded repeated unit.

Cards are not the default container for all content.

Before using a card, ask:

```text
Does this content need independent grouping?
Does it repeat?
Does the boundary improve comprehension?
```

If not, prefer:

```text
open composition
dividers
columns
typographic hierarchy
surface shifts
```

---

# 19. Action Hierarchy

Prefer one clearly dominant action per context.

Primary actions may use Unfict Blue.

Secondary actions should remain visibly secondary.

Avoid:

- clusters of equally loud buttons;
- repeated CTA buttons in every section;
- fake urgency;
- aggressive conversion patterns.

Current primary public action is generally:

```text
Request developer preview
```

Page-specific authority controls final CTA wording and placement.

# 22. Job Before Platform

Preferred:

```text
what the visitor needs to accomplish
```

```text

```

```text

```

before internal architecture vocabulary.

---

# 23. No Proof Theater

Do not visually imply trust, verification, compliance, security, or authority merely through:

```text
shields
locks
green checks
badges
certification-like seals
```

unless the underlying content explicitly supports that meaning.

Evidence, verification, Trust, Authority, Standing, and Policy are distinct concepts.

Visual design must not collapse them.

---

# 24. No Semantic Strengthening

Stitch SHALL NOT turn qualified copy into stronger visual claims.

Do not convert:

```text
"in development"
```

into:

```text
"production ready"
```

through badges, labels, status indicators, or confident UI treatment.

Do not convert:

```text
"private preview"
```

into:

```text
"available now"
```

through visual implication.

---

# 25. No Capability Leakage

The public site should not expose features merely because they exist or may exist internally.

Do not invent sections for:

```text
MCP
agents
SAP
Host-native extensions
governance consoles

policy engines
future registries
```

unless the page mandate explicitly authorizes them.

---

# 26. Accessibility

Target:

```text
WCAG 2.2 AA
```

Stitch design should preserve:

- adequate contrast;
- clear focus potential;
- sufficient target size;
- readable body copy;
- sensible heading hierarchy;
- mobile reflow;
- non-color-only meaning;
- text-equivalent consideration for diagrams.

Production accessibility will later be completed by repository implementation.

The visual design should not create avoidable accessibility debt.

---

# 27. Responsive Web — Not App UI

Every page is a responsive Web experience.

Primary design proof:

```text
desktop around 1440px
```

Required mobile proof:

```text
around 390px
```

The composition must remain viable at:

```text
360px
```

and should not collapse at:

```text
320px
```

Do not design a mobile-native app screen.

Do not use bottom-tab navigation unless a future mandate explicitly requires it.

---

# 28. Mobile Principle

Mobile is not merely:

```text
desktop
→ stack everything
```

Mobile should preserve:

```text
context
meaning
primary action
reading order
technical comprehension
```

while reducing:

```text
simultaneous density
ornament
multi-column breadth
```
